## 1. 问题定义

原《功能需求文档.md》架构决策 D7 暂定"文件即真相，不引入 sqlite 作为主存储（RAG 索引除外）"，依据是 CodeWave 与 metis 两个对标产品的一致选择。本调研对该决策做系统论证，回答三个子问题：

1. 消息历史、配置、统计等各存储对象，在文件与数据库两种方案下的适配度如何？
2. 业界同类产品（Coding Agent / 桌面 Agent）实际怎么选，付出了什么代价、踩了什么坑？
3. SQLite 在桌面场景有哪些结构性风险？文件方案的真实工程成本是多少？

**评估维度**（桌面本地应用视角）：崩溃安全、损坏爆炸半径、用户可见性/可编辑性、云同步兼容性、查询能力（搜索/聚合）、分支树表达、并发写、schema 演进、备份与 GC、工程成本。

## 2. 存储对象盘点与访问模式

CraftWave 全部持久化数据（按《功能需求文档.md》§3.4）分 11 类，各自访问模式差异极大——**这是"单一方案选边站"不成立的根本原因**：

| # | 存储对象 | 体量 | 写模式 | 读模式 | 关键约束 |
|---|---|---|---|---|---|
| 1 | 消息历史（含树状分支） | 大（长会话 MB 级，全库 GB 级） | append-only 为主；分支=fork 新段 | 打开会话全量重放；压缩后部分重放 | 崩溃零丢失（NFR-06）、分支可恢复、可审计 |
| 2 | 会话索引（列表） | 小 | 每次会话变更小更新 | 启动全量读、列表页高频读 | 启动延迟敏感（NFR-01 < 2s） |
| 3 | 工具结果边车 | 中 | 一次写、偶尔更新 | 重开恢复按 call_id 点查 | 键值模式；永不出网 |
| 4 | 媒体 blob（图片等） | 大 | 内容寻址一次写 | 按 hash 点查 | 去重、GC |
| 5 | 配置（config/project/mcp） | 小 | 低频、人工可改需求高 | 启动读 | 人可读可编辑可分享；版本迁移 |
| 6 | UI 状态 | 小 | 高频小写（防抖） | 启动读 | 丢一份无伤大雅 |
| 7 | 用量统计 | 小-中 | 每请求累计、按日聚合 | 面板查询（按日/模型/会话） | 聚合查询需求 |
| 8 | 跨会话搜索索引 | 派生 | 随消息写入增量 | 关键词查询 | 仅 FR-01-15（P2）需要 |
| 9 | RAG 向量索引（P2） | 中-大 | 索引构建批量 + 增量 | ANN 查询 | 高维向量 + 全文，本质需要 DB |
| 10 | 日志 | 大 | append-only | 尾部读、按会话过滤 | 保留期清理 |
| 11 | 信任/凭据引用 | 极小 | 极低频 | 启动读 | 事务敏感；凭据本体在系统钥匙串 |

## 3. 业界实践证据

### 3.1 同类产品存储选型一览

| 产品 | 形态 | 会话真相存储 | 派生/索引层 | 来源 |
|---|---|---|---|---|
| **Claude Code** | CLI | 每会话一个 JSONL：`~/.claude/projects/<项目路径变换>/<会话uuid>.jsonl`，每行一条类型化消息记录 | 无专门索引（恢复靠扫描文件） | 官方行为，社区广泛文档化；格式被官方声明为**内部格式、跨版本不稳定** |
| **Codex CLI / Desktop** | CLI + 桌面 | append-only JSONL "rollout" 文件：`~/.codex/sessions/<日期>/rollout-<时间>-<uuid>.jsonl`，含全部转录 | Codex Desktop 以 SQLite 作**派生索引**；有分析确认"记录先落 JSONL，数据库只是追赶"——**JSONL 是真相源，DB 是缓存** | 官方仓库与社区分析 |
| **Gemini CLI** | CLI | 每会话一个 JSONL：`~/.gemini/tmp/<项目hash>/chats/session-*.jsonl` | 无 | 官方文档（2025-12 起官方 session management：自动保存/搜索/resume/rewind） |
| **OpenCode** | CLI/TUI | **单库 SQLite** `opencode.db`：sessions/messages/parts/todos/shares/permissions/projects/credentials 全在一个库 | 库内 | 社区深度分析文章 |
| **Cursor CLI** | CLI | 未公开的 SQLite `.db`（blobs/meta 表） | 库内 | 社区逆向分析 |
| **CodeWave 0.14**（对标①） | Tauri 桌面 | 分段 append-only JSONL（200 条或 512KB 封口，段水位边车 + 前缀指纹防覆盖）+ 全文件目录布局（索引/边车/blob/统计/日志全是文件） | 无独立索引库（index.json + 按需扫描） | 本地代码库调研 |
| **metis 2.0**（对标②） | Electron 桌面 | 树状 JSONL v3：每条 entry 带 `id/parentId` 构成消息树，压缩/分支摘要也是 entry 类型 | `sessions-index-v1.json` 会话索引**缓存**（首行头快速解析加速冷启动） | 本地代码库调研 |
| **rig 0.46**（本项目内核） | Rust 框架 | **默认 JSON-lines**（`rig-session/4` 规范格式）：支持 resume/rewrite/**fork 到轮次边界**；append 前校验日志长度（乐观并发，并发写第二次被拒）；格式迁移链逐步升级且**旧格式原样保留在 `rig/kept/`** | `rig-sqlite` 提供 `SqliteSessionStore`（可选后端）：三张表（logs/log_chunks/files），head 行存日志长度、每次 append 只写新增 chunk、单条 IMMEDIATE 事务含长度校验；官方定位是"每个打开该文件的进程共享会话"的**多进程/服务端**场景，另有 rig-postgres | 本地代码库调研 |

**统计**：8 家中 **6 家**（Claude Code、Codex、Gemini CLI、CodeWave、metis、rig 默认）以**文件为会话真相源**；唯一以单库 SQLite 为真相源的 OpenCode 恰好暴露了该路线的最大教训（下节）；Cursor 的 SQLite 不公开不可读。Codex Desktop 代表了第三条路——**文件真相 + SQLite 派生索引**，正是本调研推荐的路线。

### 3.2 关键案例剖析

**OpenCode：单库 SQLite 的膨胀与搜索困境。** 社区实测文章《Garbage collecting OpenCode's 2.4 GB session database》记录：OpenCode 把每轮完整思考/推理输出全部入库，导致数据库膨胀到 2.4GB，其中真正有意义的对话文本只占约 1%，需要专门写 GC 工具清理；同时因库不可读、搜索能力弱，社区又出现了第三方工具（mnemo）把库**再索引**到另一个 SQLite 里做全文搜索——**单库方案既没防住膨胀，也没换来搜索便利**。

**Codex：JSONL 先行、DB 追赶，以及单行损坏的启示。** Codex Desktop 的架构分析确认记录总是先写 JSONL、SQLite 索引异步追赶；同时它有一个已知 bug（openai/codex#24425）：rollout 文件中一行 JSON 损坏，会话就从线程列表消失——尽管文件本体还在。两个启示：① 派生索引**必须**有"从真相层重建"的自愈路径，且损坏时宁可降级不可隐藏数据；② append-only 文件的单行损坏应只损失该行，读取端要容忍尾部/单行残缺（跳过并告警），而非整体拒绝。

**SQLite × 云同步：官方确认的结构性风险。** SQLite 官方文档《How To Corrupt An SQLite Database File》明确：SQLite 依赖数据库文件与 WAL/`-shm` 边车上的**文件锁**协调并发，而 Dropbox/iCloud 等同步服务不理解锁、会把库文件与边车在不同时刻分别上传，产生不一致快照；WAL 模式下失败同步可能在校验点（checkpoint）时固化损坏（可用 PRAGMA 缓解但无法消除）。社区大量实证（Joplin、RootsMagic 等应用的论坛灾情帖）：活跃 SQLite 库直接放同步目录是桌面应用的经典损坏源；甚至 Time Machine 备份活跃库也有风险。桌面用户"把数据目录丢进 iCloud/Dropbox/Syncthing 多机同步"是真实高频行为，**这直接否决"以 SQLite 单库为唯一真相"的方案**。

**CodeWave：文件方案的工程代价（诚实盘点）。** CodeWave 以约 12 万行 Rust 实践了纯文件方案，为弥补"没有数据库"付出了真实的自建成本：

- **索引一致性**：会话索引 index.json 的维护需要锁序纪律（先 save_lock 后 index_lock）防竞态；
- **崩溃安全**：全部写入走原子写（临时文件 + rename，Windows 用 MoveFileExW），历史分段配水位边车与**前缀指纹校验**——恢复时指纹不匹配只追加新段、绝不覆盖旧段；
- **对账**：因为承认"事件会丢"，还要做终态快照对账自愈；
- **容量防御**：200MB 软告警 / 1GB 熔断的机制，本质是文件方案缺少内建配额管理的补偿；
- 其可靠性修复专项计划中列出的问题（凭据落盘路径、事件丢失、历史恢复）说明文件路线的复杂度会向**流程纪律**转移——问题不是出在格式本身，而是围绕格式的每个环节都要自己写对。

**metis：索引缓存是文件方案的必要补丁。** metis 的会话树 JSONL 设计很优雅（entry 带 parentId、压缩/分支摘要/自定义状态都是 entry），但冷启动性能靠 `sessions-index-v1.json` 索引缓存解决（只解析首行头 + 索引文件，不全量读 JSONL）——证明**文件方案在"列表/搜索"场景必然需要一个派生索引层**，区别只在用 JSON 还是 SQLite 实现这个索引。

### 3.3 rig 双轨设计说明什么

rig 同时提供 JSON-lines（rig-memory，默认）与 SQLite/Postgres session store，两者实现同一 `AsyncStore` 契约、语义完全一致（append-only 日志 + 乐观并发 + 全有或全无写入）。关键细节：

- **规范格式是 JSON-lines**：`rig-session/4`，DB 后端是同一语义的替身，不是另一套模型；
- **SqliteSessionStore 的设计动机是多进程共享**（"every process that opens the file shares it"）与服务端部署（rig-postgres）——CraftWave 是 Tauri 单进程应用，该动机不成立；
- **rig-memory 的并发与迁移设计值得直接继承**：append 前一步完成"长度校验+追加"（两写者竞速，后者被拒并重读）；格式迁移链把旧格式会话**原样保留**在 `rig/kept/` 目录（与 CodeWave"绝不覆盖旧段"同一哲学，但工程化更完整）；
- **fork 到轮次边界**原生支持——与 assistant-ui 的消息分支模型（ExportedMessageRepository）语义对齐。

## 4. 两方案对比分析

| 维度 | 纯文件（CW/metis 路线） | 单库 SQLite（OpenCode 路线） | 说明 |
|---|---|---|---|
| 崩溃安全 | ✅ append-only 天然安全：损坏最多丢尾部单行；原子写覆盖配置类 | ✅ WAL 事务全有或全无 | 平手（都要正确配置：文件要 fsync 策略，DB 要 WAL） |
| 损坏爆炸半径 | ✅ 单会话隔离：一个文件坏不影响其他 | ❌ 整库单点：库损坏=全部会话不可用 | 文件显著优 |
| 用户可见/可编辑 | ✅ 文本可读、可 grep、可手改、可 git 管 | ❌ 需工具链（OpenCode/Cursor 社区被迫逆向） | 文件显著优（"本地优先"产品原则直接依赖此项） |
| 云同步兼容（iCloud/Dropbox/Syncthing） | ✅ 纯文本文件同步安全（粒度=文件） | ❌ 官方确认损坏风险（锁与 WAL 边车不被同步理解） | 文件显著优 |
| 跨会话搜索 | ❌ 需自建索引（CW 干脆没做内容搜索；metis 只有列表搜索） | ✅ FTS5 内建 | DB 优——但可由派生索引层获得 |
| 统计聚合 | ⚠️ 自己累计（CW stats/ 文件按日聚合，量小可行） | ✅ SQL 聚合内建 | 平手偏 DB；量小场景文件够用 |
| 分支/树表达 | ✅ metis 证明 parentId entry 方案成熟；rig-memory 原生 fork | ⚠️ 也能建 parent_id 表，但查询更新 | 平手 |
| 并发写 | ⚠️ 自建锁序/指纹（CW 代价实证）；rig-memory 已解决 | ✅ 事务内建（IMMEDIATE + 长度校验） | rig-memory 把文件方案拉平 |
| schema 演进 | ⚠️ 自定义迁移代码（CW schema v2 经验可控） | ✅ user_version 迁移链成熟 | 平手（rig 的迁移链+保旧设计两路线通用） |
| 备份/保留期/GC | ✅ 文件操作即完成（删文件/拷目录） | ⚠️ 需 VACUUM、膨胀风险（OpenCode 2.4GB 实证） | 文件优 |
| 启动性能 | ⚠️ 需索引缓存（metis 实证） | ✅ 索引内建 | 平手（缓存方案一致） |
| 工程成本 | ⚠️ 自建索引/锁/水位/对账（CW 千行级投入，rig-memory 可复用大半） | ✅ 存储层薄 | DB 略优，但派生索引层方案下两条都要写薄层 |

**结论**：在"崩溃安全、损坏隔离、用户可见、云同步"四个桌面应用最看重的维度上文件全面占优；DB 的真正优势只有**查询（FTS/聚合）**，而这恰好是"派生索引"可以独立提供的——**两类优点可以叠加，不必二选一**。

## 5. 推荐方案：分层混合存储

### 5.1 三条铁律

1. **唯一副本只存在于文件**：任何数据的真相（消息历史、工具结果、配置、统计累计、信任记录）只允许以文件形式落盘。SQLite 库中永远不存放任何"删了就没了"的数据。
2. **索引库可随时删除重建**：`~/.craftwave/cache/index.db` 是纯派生物。删除后：跨会话搜索降级（提示"索引重建中"）、统计面板回退到文件直读、RAG 检索暂不可用——**不丢失任何用户数据**；后台自动全量重建并显示进度。启动时做完整性校验（PRAGMA quick_check + schema 版本号），异常即弃库重建。
3. **索引库不进同步目录**：cache/ 目录在文档中明示"勿放入云同步"；真相层文件天然可同步。若用户整体同步数据目录，cache/ 自动检测并警告（同步场景下建议每次退出删除）。

### 5.2 存储对象决策表

| 存储对象 | 真相层（文件） | 派生索引库（cache/index.db） | 理由 |
|---|---|---|---|
| 消息历史（树状） | ✅ 分段 append-only JSONL（rig-memory `rig-session/4` 格式，含 parentId/fork entry） | — | 崩溃安全、分支恢复、可审计（§4 四维全优） |
| 会话索引 | ✅ `sessions/index.json`（≤2000 条，原子写） | ✅ sessions 表（启动加速冗余） | 索引文件本身小而快；DB 副本仅锦上添花 |
| 跨会话全文搜索 | —（真相即被索引对象） | ✅ **FTS5**（messages_fts 虚表，含会话/时间/模型元数据列） | FR-01-15 唯一硬需求来源；重建=扫全部 JSONL |
| 工具结果边车 | ✅ `sessions/<id>.toolres/<call_id>.json` | — | 键值点查，文件直读足够 |
| 媒体 blob | ✅ 内容寻址文件（SHA-256 前 32 hex） | — | 大二进制不入库（OpenCode 膨胀教训） |
| 配置/项目/MCP/信任 | ✅ JSON（原子写 + schema 版本迁移） | — | 人工可读可编辑是硬需求 |
| UI 状态 | ✅ `ui-state.json`（防抖） | — | 丢一份无伤 |
| 用量统计 | ✅ 按日聚合 JSONL（累计真相，小体积） | ✅ stats 表（面板查询缓存） | 真相可重算（从历史 usage 记录）；聚合查询走 DB |
| RAG 向量（P2） | —（源文档在工作区，嵌入可重算） | ✅ **sqlite-vec** 虚表 + FTS 混合检索 | 向量检索本质需要 DB；rig-sqlite 原生支持 |
| 日志 | ✅ 分会话日志文件 | — | append-only 文本 |
| 凭据 | 系统钥匙串（不变） | — | 永不入库入文件明文 |

### 5.3 派生索引库设计要点

- **位置与命名**：`~/.craftwave/cache/index.db`（目录名即语义：缓存，可删）。
- **内容**：sessions 表（列表加速）、messages_fts（FTS5 全文）、stats 表（聚合缓存）、（P2）sqlite-vec 向量表。**不存 blob、不存配置、不存任何唯一数据。**
- **维护协议**：消息落盘（真相）成功后异步更新索引（写穿队列，失败仅记日志不阻塞会话）；索引落后不影响任何 P0 功能。
- **重建协议**：手动（设置里"重建索引"按钮，配 FR-14）与自动（启动校验失败 / 版本升级 / 用户删除文件）两条路径；重建为后台任务，带进度与可取消。
- **降级行为**：索引不可用时——会话列表回退 index.json；搜索入口置灰提示重建；统计面板直读按日 JSONL（慢但正确）；RAG 检索暂不可用。

### 5.4 与既有机制的关系

- 本方案与 Codex Desktop 的"JSONL 真相 + SQLite 索引"架构同构，但把"可重建、可降级"写成硬性验收条款（规避其索引损坏即列表消失的 bug 模式）；
- 继承 CodeWave 全部文件侧纪律（原子写、分段水位、前缀指纹、绝不覆盖），并把其中"rig-memory 已内置"的部分（乐观并发 append、格式迁移保旧、fork）改为直接复用框架能力，工程成本低于 CW 重造；
- metis 的索引缓存思路从 JSON 升级为 SQLite，是其自然延伸。

## 6. 与 rig / assistant-ui 的对接

1. **真相层直接采用 rig-memory 作为会话日志引擎**：`rig-session/4` JSON-lines 格式由 rig 负责读写，CraftWave 获得 append 乐观并发、resume/rewrite/fork、迁移链（旧格式保留 `rig/kept/`）等能力而不自研；`AgentBuilder::memory` 原生接入。CraftWave 在其上叠加产品语义：分段封口策略（超大会话切段，沿用 CW"绝不切在工具配对中间"规则）、toolres 边车、imgblob、runs 元数据目录。
2. **不使用 SqliteSessionStore**：其设计动机（多进程共享文件）在 Tauri 单进程中不存在；真相层保持文件。
3. **分支映射**：rig-memory 的 fork-to-turn-boundary 与 assistant-ui 的 ExportedMessageRepository 树结构在《技术设计文档》中定义映射（PRD D8 已立项）；持久化 entry 携带 parentId，前端分支恢复零转换。
4. **RAG（P2）**：索引库内 sqlite-vec 与 rig-sqlite 的向量存储契约对接；源文档与嵌入参数记录在索引库侧，删除即彻底关闭 RAG。

## 7. 对《功能需求文档.md》的修订

本调研结论回写 PRD（v0.96）：

1. **D7 修订**：真相层文件化不变；新增"派生索引层"——允许且仅允许在 `cache/index.db`（SQLite）中存放可重建数据（会话列表加速、FTS5 全文、统计聚合、RAG 向量），受三铁律约束（唯一数据只在文件 / 可删可重建 / 不入同步目录）。
2. **§3.4 增补**派生索引层描述与本文档引用。
3. **新增 NFR-21（索引可重建性）**：删除 cache/ 目录后应用正常启动、无数据丢失、搜索/统计/RAG 按设计降级并自动后台重建。
4. **FR-01-15 注记**：跨会话内容搜索由派生索引库 FTS5 支撑。
5. **FR-14 增补**：设置页"重建索引"入口（并入诊断组）。
