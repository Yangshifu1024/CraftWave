## 1. 文档说明

### 1.1 定位

本文档回答 PRD（v1.0）中 P0–P2（里程碑 M0–M3）需求的"怎么做"，是开发、评审与测试编码工作的直接依据。详细度按里程碑递降分层：**P0（M0+M1）字段级/伪代码级**（可直接开工）；**P1（M2）契约字段级+组件级**（命令/帧/事件/存储格式完整，模块设计到接口与数据流）；**P2（M3）架构级**（接口定义与扩展点，实现方案允许微调）；P3 仅记录架构占位与触发条件。设计单元以【M2】【M3】【P3】标签标注里程碑，未标注者默认 M1。

### 1.2 编写与修订规则

- **可追溯性**：每个设计单元标注其实现的 PRD 需求编号（FR-xx-xx / NFR-xx）；完整映射见附录 B。
- **冲突处理**：本文档不得违反 PRD 的验收标准；设计过程中发现 PRD 缺陷时，修订 PRD 并在本文变更记录中注明，不允许绕开。
- **未决问题**：实现层面尚未定论的事项一律记录于附录 C（含建议默认方案），不阻塞其余章节；统一处理后从清单移除并回写正文。
- **自包含**：与 PRD 一致，本文档可脱离参考仓库源码独立交付；涉及上游库（rig/assistant-ui/Tauri）的事实均内嵌描述并标注版本。

### 1.3 术语（增量于 PRD 术语表）

| 术语 | 定义 |
|---|---|
| run / turn / step | run=用户一次发送到最终答复的完整执行；turn=run 内一次模型调用周期（模型输出→工具批→回喂）；step=帧流中的轮次计数（与 turn 同值，用于前端分组） |
| wire 消息 | 发给模型的协议中立消息（role + parts），由会话条目重建 |
| canonical 历史 | Rust 持久化的权威消息序列（会话 JSONL），前端展示树是其超集（分支） |
| 帧序列号 seq | Channel 每帧自增计数，用于对账与去重 |
| session revision | 会话修订号，每次 canonical 追加或树同步成功后 +1，用于乐观并发 |
| 镜像工具 | 前端 defineToolkit 声明的后端工具副本，仅用于渲染与结果桥接，不在前端执行 |

## 2. 系统架构总览

### 2.1 进程与运行时模型（实现 FR-13-10 单实例、D1 单进程）

单一 Tauri 2 进程：

- **WebView 进程**（React 应用）：聊天运行态（assistant-ui LocalRuntime）、应用状态（zustand）、IPC 客户端。
- **Rust 主进程**：tokio 多线程运行时（Tauri 内置）。`#[tauri::command]` async 命令运行其上；每个 run 以 `tokio::spawn` 独立任务执行，通过 `CancellationToken` 取消。
- 单实例互斥：tauri-plugin-single-instance，二次启动向既有实例转发 `activate_and_show`。
- 窗口与启动（FR-13-04、NFR-01）：自绘标题栏 = tauri-plugin-decoration 覆盖式标题栏（C-7 已定——3.0.5 × tauri 2.12 兼容，见附录 C）。激活协议（兼作防闪启动 + 亮窗看门狗）：窗口以 `visible:false` + `titleBarStyle:"Overlay"` + `hiddenTitle` 启动 → 前端调 `activate_decoration`（macOS 另调 `set_traffic_lights_inset` 定位交通灯）→ documentElement 出现 `data-tauri-plugin-decoration-active` 再亮窗 → 5s 超时调 `restore_decoration` 退化系统标题栏并无条件亮窗。冷启动预算分解——Rust 侧仅读 config + index.json（<50ms 量级），首屏只加载当前会话历史，历史加载异步于首帧渲染。
- 关闭到托盘：主窗口 close 请求拦截 → 隐藏窗口继续运行（后台运行语义，FR-13-06/07）；存在活跃 run 时经 `app:exit_requested` 事件 + `resolve_exit_request` 命令确认后退出。

### 2.2 Rust 模块划分（D9：M1 单 crate 模块化单体）

```
src-tauri/src/
├── main.rs / lib.rs        # Tauri builder、插件注册、命令注册表
├── host/                   # IPC 层：命令实现（校验/转调）、事件汇、通知、托盘、菜单、退出拦截
│   ├── commands/           # 按域分文件：system/config/provider/project/session/workspace/toolres/ui_state
│   ├── events.rs           # 事件键常量 + emit 封装（供契约测试扫描）
│   └── notify.rs           # 系统通知（三平台）+ notify:activate 回跳
├── agent/                  # 运行时：RunManager、run 状态机、steer/followUp 队列、对账快照
├── backend/                # rig 防腐层：中立 trait + RigAgentBackend + ScriptedBackend(测试)
├── providers/              # 供应商解析（CW schema v2 → rig Model）、Key 池、错误分类
├── tools/                  # 工具注册表 + 各工具实现（read/edit/command/…）+ 批次调度
├── safety/                 # 权限档过滤、审批门、命令围栏(fence)、safe_join、删除守卫、SSRF(P1)
├── storage/                # 会话 JSONL、索引、配置协调器、原子写、toolres 边车、UI 状态
├── knowledge/              # 系统提示组装器（M1：核心提示+权限档块+项目指令）；skills/memory P1
└── util/                   # atomic.rs（原子写）、ids、time、test_support
```

模块依赖方向单向：`host → agent → backend/tools/providers → safety/storage`；`tools` 与 `agent` 互相只通过接口（ToolRegistry）交互。M1 不拆 workspace 多 crate（编译时长与重构成本不划算），crate 边界以模块纪律代替，1.x 若需要再物理拆分。

### 2.3 数据流总览

```
用户发送 → Composer → ChatModelAdapter.run()
  → invoke("start_chat", {sessionId, messages, runConfig, channel})
    → RunManager 启动 run 任务：
        组装(权限档工具集 + 系统提示 + 历史重建) → RigAgentBackend.stream()
        事件流 → 帧节流(64ms) → channel.send(ChatFrame)
        工具轮 → fence/审批门(ask) → 工具执行 → toolres 边车 + canonical 追加
        终态 → runEnded 帧 + run:done 事件 + 建议生成(suggest)
  ← 前端：帧 → assistant-ui parts 累积 yield / runMetrics store / 工具卡片桥接
```

## 3. IPC 契约（字段级）

> 实现 PRD §3.3 三通道与附录 D；本节是其 P0 切片的字段级展开。契约测试见 §12.3。

### 3.1 通用约定（D14）

| 约定 | 内容 |
|---|---|
| 命令名 | snake_case，与 Rust `#[tauri::command]` 函数名一致（如 `invoke("start_chat")`） |
| 负载字段 | 一律 camelCase：Rust 结构体 `#[serde(rename_all = "camelCase")]`；TS 侧由 ts-rs 12 从 Rust 契约类型生成（`ui/src/ipc/generated/`，生成物进 git、cargo test 驱动导出；`ipc/types.ts` 只再导出，02 号票落地，见附录 C-2） |
| 可选字段 | 显式 `?` / `Option`，无 null 满字段；时间戳 epoch 毫秒 int64（TS number，JSON 序列化位数足够） |
| 错误 | 命令失败统一 reject `{ code: string, message: string, detail?: unknown }`；code 全集见 §3.6 |
| Channel | `tauri::ipc::Channel<SequencedFrame>`（线帧 = `{seq, ts?}` 基座 + ChatFrame 判别联合，Rust 侧展平发送；02 号票起 ts-rs 生成两侧类型） |
| 事件 | `emit_to("main", key, payload)`；payload 均含 `sessionId`（全局事件除外） |

```ts
  ui: { language: "zh-CN" | "en-US"; theme: "light" | "dark" | "system";
        aiLanguage?: string; fontSize?: number };   // 字号 12–18px，缺省 14
  log: { level: "debug" | "info" | "warn" | "error" };

  };

    modelId?: string;              // 专用摘要小模型（指向某 ProviderModel.id）；
                                   // 未配置时用会话 active model（§6.2）

  tools: {                         // 【M2】工具批执行（FR-03-11/FR-04-04，07 号票实装）

interface UsageTotal { input: number; output: number; cacheRead: number; cacheWrite: number; }
interface RunSnapshot {                // session_run_snapshot 返回；对账用（FR-03-08）
  status: "idle" | "running";
  runId?: string; startedAt?: number; turn?: number; toolCount?: number;
  usage: UsageTotal; lastSeq: number;  // lastSeq=已发出最大帧序号
}

// ---- 询问/审批（实现 FR-05-02/03/04）----
type AskPayload =

      questions: { id: string; text: string; options?: { id: string; label: string }[];
                   allowFreeText: boolean }[] }
  | { kind: "approval"; title: string;
      diff?: { path: string; hunks: { header: string; lines: { kind: "add" | "del" | "ctx"; text: string }[] }[] };
      command?: string; fenceReason?: string;
      options: { id: string; label: string; recommended?: boolean;
                 mode?: "allow_once" | "always_session" | "deny" }[] }
  | { kind: "mcpTrust"; server: string; transport: "stdio" | "http";      // 【M2】MCP 启动信任（FR-08-03）
      fingerprint: string; commandOrUrl: string;
      options: { id: "allow_once" | "remember" | "deny" }[] }
  | { kind: "projectTrust"; resourceName: string; fingerprint: string;   // 【M2】项目资源信任（FR-05-10）
      options: { id: "allow_session" | "remember" | "deny" }[] };
type AskAnswer =
  | { kind: "question"; answers: Record<string, string> }   // qid -> 选项 id 或自由文本
  | { kind: "approval"; optionId: string; editedCommand?: string };
```

### 3.4 Channel 帧定义（ChatFrame，P0 全集 9 种）

```
帧基座：所有帧先序列化为 { seq: number, type: string, ts?: number, ...字段 }（seq 由 Rust 端 RunHandle 递增；ts=Rust 出口 epoch ms，可选字段，供端到端延迟埋点与 §5.6 对账——S2 实证加入，向后兼容）

runStarted   { seq, type:"runStarted", runId, model: string }            // model=显示名
stepStarted  { seq, type:"stepStarted", turn: number }                    // turn 从 1 起
textDelta    { seq, type:"textDelta", turn, delta: string }
reasoningDelta { seq, type:"reasoningDelta", turn, delta: string }
toolStarted  { seq, type:"toolStarted", callId, name: string }
toolArgs     { seq, type:"toolArgs", callId, chunk: string }              // 参数增量 JSON 片段
toolResult   { seq, type:"toolResult", callId, ok, uiSummary: string,
               error?: { code: string; message: string } }
usage        { seq, type:"usage", usage: UsageTotal, rate?: number }      // rate=输出 tok/s（FR-01-13）
runEnded     { seq, type:"runEnded", reason: "done"|"error"|"cancelled",
               durationMs: number, toolCount: number, turn: number,
               error?: { code: string; message: string } }
```

排序规则：Rust 端保证 seq 严格递增且与发送顺序一致；toolResult 必晚于同 callId 的全部 toolArgs；同一调用的 toolStarted.callId 与 toolArgs.callId **同源**（= 帧面统一 id——工具参数增量阶段模型 call id 未定稿（rig 流事件只携带 part 序号），backend 桥接层以派生 id（`call_part_{turn}_{n}`，turn 前缀防跨轮撞车——part 序号按响应各自从 0 计，14 号票修正）承载流式三帧，End 事件定稿后登记「模型 call id → 桥接 id」映射，toolResult 按 callId 反查同一桥接 id；帧面三帧自洽且与模型调用一一对应，前端镜像工具卡按 callId 与 toolResult 配对，13 号票实证约定）。

节流语义（64ms，S2 实证钉死）：**首增量立即出帧，其后相邻 flush 间隔 ≥64ms**（事件驱动，非固定 tick）——朴素 tick 会让首帧平白多等一个窗口相位，损害 TTFT。NFR-02（<100ms）实测余量：Rust 侧上界 = 64ms 窗口 + 亚毫秒桥接开销（TTFT 实测 0.4ms、单帧 0.4ms），前端 FrameBuffer 处理亚毫秒，渲染余量 >35ms。

## 4. rig 防腐层

### 4.1 目标（实现 D6、风险 R1）

业务代码（agent/tools/providers 之外）不 import rig 具体类型；rig 升级只改 `backend/rig_impl.rs` 与 `providers/` 两处。

### 4.2 中立接口

```rust
// backend/mod.rs —— 业务侧唯一可见的类型
pub enum BackendEvent {
    Started { model: String },
    TextDelta(String),
    ReasoningDelta(String),
    ToolArgsDelta { call_id: String, name: String, chunk: String },
    ToolRound(Vec<ToolInvocation>),        // 本 turn 全部调用解析完毕（参数 JSON 完整）
```

### 4.3 两个实现

- **RigAgentBackend**：实现载体为 rig `run::AgentRun`（**sans-IO 状态机**，S3 实证）+ `StreamedTurnAssembler`。RunLoop 驱动单元是 AgentRun 步进（见 §5.2）：`next_step()` → `CallModel{prompt,history,turn}` 时经 `prepare_request`（RunSpec+ProviderCapabilities）→ `PreparedRequest::apply(CompletionRequest)` → `Model::stream`，流事件边经 `assembler.ingest` 记账边桥接为 BackendEvent/Channel 帧（文本/思考 delta、工具参数增量含半截 JSON），turn 末 `record_streamed_completion_call`（usage/finish_reason）+ `run.streamed_turn()` 收口；`CallTools{calls}` 时宿主执行工具并 `answer_all` 回喂。**审批挂起 = CallTools 步骤上把整只 run `serde_json` 序列化挂起、反序列化恢复继续**——天然支持跨重启恢复审批（S3 实证），backend 无需改为 AgentHook::Dispatch 拦截路线。确证点见附录 A Spike S2/S3。
- **ScriptedBackend**：按脚本回放 BackendEvent 序列，供全部 agent 层单测/集成测试使用（无网络、确定性、毫秒级）。
- **M1 落地注记（13 号票）**：backend 落地为 `drive_run` RunLoop 直产 ChatFrame（rig `Model` 由命令层装配、RunLoop 经 `TurnDriver` 驱动， rig 依赖仍收敛于 backend/turn+rig_bridge 两文件）；`BackendEvent` 中间 trait 与 `ScriptedBackend` 在单后端（openai_chat）实现下暂缓——防腐目标（升级只改 backend/providers）由模块边界与测试面（mock OpenAI 端到端 + Scripted 面按需补）承载，多后端场景出现时再抽。

### 4.4 版本与升级策略

- 锁定 `rig = "0.45.0"`（S2/S3 双版本实证：0.45.0 与 0.46.0-rc.1 宿主代码零改动全绿、延迟同量级，见附录 C-6）。**MSRV 随 rig 走**：rig 0.45.0 要求 Rust 1.97.1，rust-toolchain.toml 已自 1.97.0 抬升。
- 升级流程：单独 PR → ScriptedBackend 全量回归 + 真实 provider 冒烟（人工）→ 合并；MIGRATING.md 为必读清单。注意 cargo pre-release 匹配规则：需求串 `0.46.0-rc.1` 不会自动升级到 0.46.0 stable，换版必须手动改。

### 5.3 run 状态机（FR-03-01/02/03/06）

```mermaid
stateDiagram-v2
  [*] --> Streaming: start_chat
  Streaming --> AwaitingTool: ToolRound(免审直执行工具)
  Streaming --> AwaitingApproval: ToolRound(需审批/ask)
  AwaitingTool --> Streaming: 工具结果回喂(下一 turn)
  AwaitingApproval --> Streaming: resolve_ask(allow)
  AwaitingApproval --> Cancelled: resolve_ask(deny)/cancel
  Streaming --> Done: End(done)
  Streaming --> Error: End(error) 且不可重试
  Streaming --> Retrying: End(error) 可重试（≤6 次退避）
  Retrying --> Streaming
  Done --> [*]
  Cancelled --> [*]: 补齐 cancelled toolResult → runEnded(cancelled)
  Error --> [*]
```

不变量：终态前三件事必做——取消中工具收齐（补 `E_CANCELLED` 结果）、canonical 追加 runMarker、快照 status 置 idle。取消传播（S5 实证，全链远低于 1s）：`cancel_run` 置 CancellationToken → ① 模型流停止：流循环 `tokio::select!(biased; token.cancelled(), stream.next())`，token 胜出即 drop HTTP 流（实测 0.03–0.06ms）；② 命令进程组收割：命令 spawn 即入独立进程组（Unix `process_group(0)`，取消时 SIGTERM → 宽限 200ms → SIGKILL 整组，孙进程随组消亡，实测 6–8ms；Windows Job Object：`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` 兜底 + `TerminateJobObject` 整树，MSVC target 可编译性已验、运行行为由三平台 CI 覆盖，生产落地以 `CREATE_SUSPENDED` 消除 spawn→assign 窗口的后代逃逸，§8.3）；③ 工具结果收齐补 `E_CANCELLED`：被收割/未执行工具 `toolResult.ok=false` + `error.code=E_CANCELLED`，已完成结果原样保留（已写文件不回滚）；收齐后才发 `runEnded(cancelled)`，必为最后一帧（`error?`/`reason=cancelled` 均为 §3.4 现有字段，帧协议零修订）。

### 5.4 工具门控与执行（RunLoop 内）

每个 ToolRound：① 权限档排除（E_TOOL_BLOCKED 帧内标记，不中断 run）→ ② 同批写路径冲突检测（M1 串行执行 + edit 唯一匹配语义天然收敛，批次事务预演为 M2，14 号票论证；07 号票落地）→ ③ fence（command 专属，Allow/Confirm/Block）→ ④ 审批门（confirm_each 档的写类/网络类，或 fence=Confirm）→ ⑤ 执行（【M2 07 号票定稿】受控并发：先策略门筛选真正执行的调用（Q35/Q42 ask 互斥），再批级门控预判（Suspend 挂起零执行），随后 tokio JoinSet 并发——FileWrite 能力（write/edit）走进程级全局互斥队列**跨会话串行**（防两会话同写一文件），ReadOnly/Meta/Network 无冲突并发、信号量额度 = `tools.maxParallel`（缺省 4，§3.2）→ 收集后**按源序**发 toolResult 帧并 `answer_all` 回喂（完成顺序不改序）→ ⑥ 双通道结果（帧 toolResult；toolres 边车落盘随持久化票）→ ⑦ 模型侧 compact 文本回喂（§8.2）。取消收齐为 S5 不变量的并发版：cancel 置位 → 停止派发未开始任务 → join 全部在飞任务（命令类走既有进程组收割 §8.8/S5）→ 已完成结果保留、未派发调用补 `toolResult.ok=false + error.code=E_CANCELLED`（`ToolExecution::Cancelled{executed}` 的"未派发/在飞被收割"两态映射）→ 才发 runEnded(cancelled)。

审批实现（14 号票落地口径）：**批级门控预判**——CallTools 先对整批判定再执行，首个 Suspend 即把整只 run 序列化挂起（**挂起时批内零执行**，恢复后 `next_step` 原样重放全部 calls，无重复副作用；13 号票「逐个判定逐个执行」形态存在挂起前已执行调用被重放的问题，本票修正）；恢复以 `DriveState` 延续计时/usage 累计/工具计数与 callId 映射（不重发 runStarted、usage 不回退、toolResult 与挂起前流式帧同源）。挂起等待在 host run 任务：注册 AskSlot → `ask:opened` 事件携带 AskPayload → `resolve_ask`/取消/autoConfirm 300s 超时自动 recommended → allow 则按「(name, argsJson) 签名」登记放行并 `resume_run` 续跑（同签名放行避免恢复重放死循环）；deny/取消 → 挂起调用补 E_CANCELLED 拒绝结果帧 + runEnded(cancelled)（§5.3 AwaitingApproval → Cancelled）。默认无限等待。

**ask 混批（Q35，07 号票落地）**：一个批次同时含 ask（Interactive 能力）与其他工具时，只执行 ask；其余调用逐一明确返回"未执行，等待回答后重新决定"，模型看到回答后重新发出调用。不能先问完再照旧参数执行其余工具。先筛选真正执行的调用，再沿用门控预判与挂起零执行规则；被跳过调用不执行、不申请审批，但调用/结果配对仍须完整。**未执行结果的错误码与帧/恢复契约（07 号票补齐）**：被跳过调用按工具级失败收口——`toolResult.ok=false + error.code=E_TOOL_SKIPPED`（§3.6，uiSummary 注明"等待回答后重新决定"），模型通道回喂 `E_TOOL_SKIPPED` + 说明文本；该结果不视为 run 失败（run 继续，与 Blocked 同型的帧内标记）；帧面按批内源序在 ask 结果帧之前发出（源序回喂）。恢复语义：挂起重放恢复时策略门重新筛选（判定与参数无关、天然一致），被跳过调用不申请审批、不留悬空；审批挂起的 Suspend 判定只在真正执行的调用上做出（被跳过项不触发挂起）。

**多个 ask（Q42，07 号票落地）**：同批只执行源序首个 ask，其余 ask 也明确返回未执行（同 E_TOOL_SKIPPED），模型收到首个回答后再决定下一问；互不依赖的问题可放同一份问卷的 questions 中。停止操作仍取消整个 run，不新增跳过协议。

### 5.5 steer / followUp（FR-01-07，06 号票字段级定稿）

- 运行中 `inject_run_message`（§3.3 #21，`mode` 入参分叉）：入 `steer_tx`（挂在 RunHandle 的会话内插话队列）；消费点=turn 边界（工具批结果回喂后、下一次 model 调用前）——追加 user 条目并注入下一请求；回执 `run:inject{acceptedAtTurn, entryId, text}`。带图消息（P1）不入 steer，进 followUp。
- **steer 条目的树承载与 id 规则（2026-10-30 回写定稿）**：Rust 侧消费点以 id `{runId}:steer:{n}`（n 从 1 起、run 内递增）直接 `append_canonical`（父=消费时刻 canonical 链尾，§7.3 时机表）；§3.4 无 user 消息帧，前端以 `run:inject` 回执**本地插入**时间线节点（带「插话」徽标，不入 assistant-ui LocalRuntime 树），runEnded 后的 canonical 树重载按同 id 收养为普通 user 消息（徽标按 id 前缀 `{runId}:steer:` 保留识别）；`save_session_tree` 的「仅追加缺失节点」语义（§6.3）保证前端树暂缺该节点时 Rust 已落条目不丢失、不漂移。
- run 结束后 `inject_run_message`：**【M1】前端驱动**——前端收到 runEnded 且本地有待发队列时自行重新 start_chat；**【M2】后端会话级 followUp 队列（`host/followup.rs`，`sessions/<sid>.queue.json` 持久化，§7.7）**：仅 run 正常完成后（runEnded 帧发出 + `RunManager.remove` 之后）自动投递队列头并新开 run（出队前复查无活跃 run——runEnded 与 remove 之间有并发 start_chat 撞 E_SESSION_RUNNING 时队列头回队延迟重试，投递循环不丢消息）；**run 失败（error，含 E_RUN_STALLED）则暂停队列**（暂停态随 queue.json 持久化，跨重启保留）、持久保留全部待发消息，等待用户明确继续（`resume_followup_queue`，§3.3 #59d）；恢复旧升级备份后全部队列保持暂停（Q41，恢复标记接线由 33 号票协调）。新 run 复用同一 Channel 语义经 attach_run（§5.8）向已重连的前端转发帧（附录 C-3 已按此定案）：自动投递的新 run 后端侧无前端通道，帧枢纽仅入环不下发（`DetachedSink`），前端收到 `run:start` 事件且本会话非运行态时走 attach 观察态（§5.6）续流，runEnded 收口重载 canonical 树。
- run 正常完成时 steer 队列的未消费残余自动转入本会话 followUp 队列尾（随下次投递发出）；run 失败时 steer 残余随 `run:queue` 的 `returned` 数组交还前端草稿（未消费的插话未落 canonical、未上时间线）。
- 取消 run：清空本会话 followUp 队列（含持久化文件）+ steer 未消费残余一并交还（`run:queue` 的 `returned` 数组），前端收到 `run:cancelled` 后清空本地队列态并回填草稿区展示（FR-01-07「返还草稿」）。

- **更新安装门（2026-10-29 用户决策）**：运行时允许检查和下载更新；应用内任一会话有活跃 run 或待审批请求时，禁用安装与重启。有待发队列时，用户须先明确暂停并保留队列才能更新；已暂停队列保持持久化，更新后仍待用户明确继续。更新流程见 §10.7 与 M2 33 号票。

### 5.6 对账协议（FR-03-08，NFR-07）

- 前端持有 runEpoch：每次收到帧 seq 必须 > 已见最大 seq，否则丢弃；缺口（seq 跳跃）触发 `session_run_snapshot` 拉取。
- runEnded 帧丢失兜底：前端 5s 未收到新帧且快照 status=idle → 调 `load_session` 重载 canonical 终态。
- WebView 重载（channel 失效）：【M1】快照显示 running → 渲染只读"运行中"态，run 由 Rust 继续执行并持久化，结束后刷新可见；【M2】经 `attach_run` 无缝重连接收后续帧（§5.8，附录 C-1 已定案）。

- **待审批恢复（2026-10-29 用户确认，05 号票实装）**：WebView 重连时从后端查询仍有效的待审批请求，恢复原始操作与参数；已失效请求关闭。查询与实时事件按请求标识对账并校验有效性，重载本身不批准或拒绝。字段级契约（§3.3 #59c）：`session_pending_ask { sessionId } → SessionPendingAsk | null`，`SessionPendingAsk = { askId, runId, kind: string, payload: AskPayload }`——payload 即开启时的原始载荷（approval 含 diff/command/围栏原因与选项，question 含问卷），由 ask 槽在注册时留存；有效性以后端 ask 槽为权威（槽位收口即查不到），无未决 ask 或 sessionId 未知 → null。前端恢复面：查询命中 → 按 askId 登记 AskPanel（原始操作与参数照常展示可批可拒）；随后收到 ask:closed(同 askId) 或 resolve_ask 返回 E_NOT_FOUND 即关闭，重连期间已解决的请求不残留可操作弹窗。

### 5.7 监督看门狗【M2】（FR-03-07）

RunState 内维护滑动窗口计数器（`VecDeque<(调用签名, 结果)>`，容量 32；签名=工具名+参数哈希），在 turn 边界评估：

| 信号 | 阈值 | 动作 |
|---|---|---|
| 同签名工具连续失败 | 3 次 | 纠偏：注入 hidden system 提示（要求换方法），不入用户可见树 |
| 同签名工具连续失败 | 5 次 | 终止 run（Error，code=E_RUN_STALLED，message 注明重复失败） |
| 无进展轮次（无文本无工具成功） | 8 / 14 步 | 纠偏 / 终止 |
| 同参数只读调用成功重复 | 4 次 | 纠偏（提示已获得过该结果） |
| 同文件连续分段读 | 10 次 | 纠偏（提示改用 batch_read） |
| 模型流停滞（请求阶段无有效模型增量） | stall_timeout 默认 300s（5–3600 可配） | 终止（E_RUN_STALLED） |

**计时边界（Q33）**：仅模型请求阶段计时，从请求发出开始，收到有效模型增量时刷新；工具执行、人工审批、子代理排队或执行的等待不计入这 300 秒，各自遵循对应超时和取消规则。前端重连、UI 帧或工具进度不刷新模型停滞计时。本体由 M2 37 号票承载，34 号收口前完成。

**字段级接缝（37 号票实装定稿）**：

- **有效模型增量判定**：流事件桥接（§4.3）产出的三类增量帧——textDelta / reasoningDelta / toolArgs——到过一个即刷新计时（三者正是模型侧内容在增长的唯一信源）；part 生命周期事件（Start/End）、未建模透传负载与帧面其他帧（stepStarted/toolStarted/toolResult/usage/compactDone 等）一律不刷新。刷新点在流循环的出帧回调内（同步、先于 64ms 节流器），不经帧枢纽与前端通道——因此 UI 帧、attach_run 重连、工具进度天然不能续命。
- **计时与恢复状态**：停滞计时器随单次模型请求生灭——`drive_run` 每拍 CallModel 以 `select!` 让「流式调用」与「停滞截止」竞争，截止胜出即丢弃在飞 HTTP 流（与取消同形），按终止路径收尾；审批挂起时 `drive_run` 已退出（计时器随之销毁），恢复后重新驱动、计时重新开始，审批等待天然不计入。工具窗口（`VecDeque<(签名, 结果)>` 容量 32、无进展步计数、各信号纠偏水位）挂在跨挂起延续的驱动状态 [`DriveState`] 上，恢复不丢历史、不重复计数。
- **终止收尾**：走既有 Error/E_RUN_STALLED 收尾——`runEnded(error, { code: E_RUN_STALLED, message })` 只发一次（已输出文本与工具结果帧保留、不撤回；触发批已执行的工具不重放副作用），`run:error` 事件 code=E_RUN_STALLED，followUp 队列按失败暂停（§5.5）。纠偏为 hidden system 提示：仅注入下一拍模型请求的 history（system 消息），不落 canonical、不进用户可见消息树；纠偏提示按信号各带水位（同阈值只纠偏一次，重复越线再次纠偏）。
- **配置**：`watchdog.stallTimeoutSecs`（§3.2 watchdog 组）按 run 装配时读取生效；归一化校验 5–3600、非法值拒绝整份提交（§7.6）。

### 5.8 帧重放与 attach_run【M2】（FR-03-08/NFR-07 补强，附录 C-1 定案）

- RunHandle 持环形帧缓冲 `VecDeque<SequencedFrame>`（FrameHub 枢纽，容量 512，溢出丢最旧并记 dropped 计数）：seq 递增 → 入环 → 下发收进枢纽（§3.4 帧基座出口），重放帧原样携带 seq/ts；发送失败（webview 已重载）不影响入环。
- `attach_run(sessionId, channel, sinceSeq)`：重放 `(sinceSeq, 当前头]` 区间帧（原 seq 不变，前端按去重规则忽略已见）→ 将 frames 接收者热切换到新 channel。触发场景：webview 重载/崩溃恢复、前端路由重建、（M3）多窗口。重放与热切换在枢纽锁内完成——切换后新帧必在全部重放帧之后经新通道发出，帧序严格不乱。
- 重放窗口耗尽（sinceSeq 落在环形缓冲之前，即 `(sinceSeq, 缓冲最旧帧)` 存在不可见缺口；典型如 dropped>0）时补发一次 `runSnapshot` 摘要帧（§3.4 定名，负载对齐 §3.2 RunSnapshot 运行中形态），前端据此整体对账。摘要帧占用一个新 seq 号、不进环形缓冲。
- 命令面幂等语义（§3.3 注记）：无活跃 run 或 sessionId 未知 → `{ replayed: 0 }`（runId 省略），不报 E_NOT_FOUND；run 结束后（已从注册表摘除）attach 同样得到空重放。

### 6.1 存储条目（会话 JSONL 每行一个，serde tag=kind）

```
{"kind":"session","v":1,"id","projectId?","createdAt"}
{"kind":"message","id","parentId?","role","parts":[WirePart…],"createdAt","runId?","status?"}          // status? 仅 assistant（MessageStatus，S4 增补）；M1 只落 complete，roundtrip 实测稳定
```

### 6.2 wire 重建（canonical → 模型输入）

按 activeLeafId 所在路径从根到叶收集节点，展开 parts：text/reasoning 原样；toolCall+toolResult 配对合并为模型工具消息；planSnapshot → 系统注入当前计划；runMarker 跳过。**【M2】系统级注入次序（03 号票定稿）**：wire history 头部的 system 前缀按 **customPrompt → 压缩 summary → 当前计划** 次序层叠——`agent.customPrompt`（FR-09-06）非空时注入为 history 首条 system 消息（最前），压缩 `summary`（路径上最近 `compaction` 条目）紧随其后，计划快照注入再后；空/未配置的层零注入。customPrompt 经 `save_config` 即时生效于下次 run（ConfigStore 缓存热替换，§7.6），不进消息史册、不计 token 预算外负担（预算检查 §6.2 下文覆盖系统指令面）。**【M2】压缩边界**：路径上最近 `compaction` 条目生效——其 `summary` 作为 system 前缀注入，`cutEntryId` 之后的条目正常展开、之前的全部跳过；token 预算超限（模型窗口 ×0.9）时优先压缩；不得静默裁掉未经摘要的历史；压缩失败的继续或暂停规则见下文压缩调度。**【M2】image part**：vision 模型映射为多模态 content 块（blob 经 Rust 侧读取 base64）；非 vision 模型的历史图片降级为 `[image: <hash>; 当前模型无法查看此图片]` 占位文本，允许继续纯文字聊天；界面原图保留并提示模型看不到（Q30 用户确认）。本次新附图及 read(kind=image) 拒绝并提示切换视觉模型；新输入与持久历史须后端区分，不能仅信任前端历史标记。临时会话 roots=数据目录下 `workspace/` 子目录（C-8 复判收窄，§9.1）。

**【M2】压缩调度（FR-03-05）**：阈值=上下文占用 ≥ compact_threshold（默认 0.6，窗口占比）；触发点=run 开始前与 ask 关闭后；流程：完整转录先落盘（不改）→ 摘要模型调用（active model 或专用小模型，超时 compact_timeout 默认 180s）→ 写 compaction 条目 + 事件 run:compacted；失败发 run:compact_failed；原上下文仍能放入模型窗口时继续，放不下时暂停并保留输入，提示重试压缩或开启新会话；不得通过静默裁掉未经摘要的历史继续执行；手动压缩命令 `compact_session`（M2 命令，参数 `{ sessionId }`，§3.3 #59b；运行中拒绝 E_SESSION_RUNNING）。**两触发点的生效面（04 号票定稿）**：① run 开始前——start_chat 在首个模型调用前完成完整压缩编排（摘要 → compaction 条目落盘 → wire 按新边界重建），本次 run 的全部请求立即生效；② ask 关闭后（wait_approval 收口处）——安全点语义下的**落盘面压缩**：审批应答后若占用达阈值则执行摘要并落盘 compaction 条目，对当前 run 恢复后的请求不回溯生效（rig 0.45 `AgentRun` 状态机不支持中途替换内部 history，序列化现场不可改写），边界自恢复后的落盘条目与下一个 run 起生效；恢复后请求超硬预算（窗口 ×0.9）时 run 以错误终态收场、输入保留，不静默裁历史。**tokensBefore/tokensAfter 口径**：压缩前后「本次实际发送内容 + 回复预留」的估算 token 数（估算器见下文），非累计消耗。

**每请求预算检查（2026-10-29 用户确认 Q18）**：每次请求前检查实际发送内容并预留回复空间，覆盖系统指令/工具定义/摘要/历史/新输入/工具结果/图片、首次请求与模型切换；最近 usage 仅校准估算，不能代替本次检查。超预算先压缩，仍放不下则暂停并保留输入，不静默裁历史。上下文占用与累计 token 消耗独立；**字段级预算规则（04 号票钉）**：占用估算 = 估算器（文本按 CJK 字符 ×1.5、其他字符 ÷4 上取整，宁高勿低；工具定义按名称+描述+schema 文本同法）对「系统前缀 + history + prompt + 工具表」求和，加回复预留（`ProviderModel.maxTokens`，缺省 32768）；自动压缩判定 = 占用 ≥ `contextWindow × threshold`；硬预算 = `contextWindow × 0.9`（wire 重建超限即触发压缩优先，压缩后仍超 → E_CONTEXT_OVERFLOW 暂停）；contextWindow 取 `ProviderModel.contextWindow`（§3.2 缺省 128000）。估算不依赖 usage 帧到达，首轮请求即可判定。

**摘要调用与分块（Q31/Q38 字段级）**：摘要 prompt 输入 = 上次有效摘要（首次压缩无）＋ 其边界之后、本次待压缩的新增内容，文本化为逐条目块（`[user] …`/`[assistant] …`/工具调用与结果带工具名、callId 与 `[tool]`/`[result ok|err]` 来源标记）；输出 = 结构化摘要正文。prompt 骨架：`把以下对话内容压缩为一份结构化摘要，供后续对话作为唯一早期上下文使用；须保留用户目标与约束、已做出的关键决定、重要文件路径/命令/事实、未完成任务与下一步，直接输出摘要正文。`单块超过摘要模型窗口（取摘要模型的 contextWindow）时按条目边界分块顺序摘要再合并（Q38：超大已完成工具批次仅在摘要输入中转为带来源标记的普通文本参与分块，原始记录与正式配对不动）；全部调用共用 compact_timeout 总预算（默认 180s，不能按块重置），实际用量全部计入会话（tokens:update 照发、不计 turnUsage）。中途失败不提交新 compaction 条目、不推进边界，保留原历史和上次有效摘要，沿用上述失败兜底。

**压缩边界完整性**：边界只落在已完成条目之间，正式对话中的工具调用与结果保持配对；待审批或未完成批次不能被压走，摘要写入不改变正在挂起的 AgentRun 状态。单个已完成批次超过摘要窗口时，可仅在摘要请求内转为带工具名、callId 和来源标记的普通文本再分块（Q38），原始记录与正式对话配对保持完整；仍遵守压缩总超时与失败不推进边界。

### 6.3 前端树 ↔ ExportedMessageRepository（D8）

- 加载：`load_session` 返回全量 entries + activeLeafId → `entriesToExported()` 构造 assistant-ui 导出结构 `{ headId, messages: [{ message, parentId }] }` → `thread.import()` 还原（内部父先子后拓扑排序）或作为 `initialMessages` 传入 `useLocalRuntime`。导出结构精确形态（C-4 已定，S4 实测钉死）：id 内嵌 `message.id`（节点无平级 id 字段）；`parentId` 必填、`null`=根（存储条目映射 null→省略字段）；顶层 `headId?: string|null` 即 activeLeaf（可缺省，缺省取 messages 末条；空树为 null）。
- 运行中：LocalRuntime 自动维护树；adapter 每次 yield 增量更新叶节点。
- 运行结束/分支操作后（编辑重发、切换分支）：前端调用 `save_session_tree(messages, activeLeafId, baseRevision)` 全量同步——Rust 校验既有 id 的内容哈希不变（变则 E_SESSION_REV），仅追加缺失节点（按父先子后拓扑序），更新 activeLeafId 与 revision。载荷为 `thread.export()` 的**全树**（含全部分支节点，非仅活动路径），导出顺序与 Rust"父先子后仅追加"天然匹配，无冲突路径。
- **canonical 双写协议（15 号票定稿）**：run 产物条目由 Rust `RunRecorder`（帧观察器，host 层装饰 sink）按 §7.3 落盘，**canonical assistant 条目 id 规则两侧同源派生**——文本 turn `{runId}:{turn}`、工具 turn `{runId}:{turn}.tools`、runMarker `{runId}:marker`（帧面 runStarted/stepStarted 可推）。前端树运行态节点（assistant-ui 单 run 单消息，id 由 runtime 分配）**不进 save 载荷**：发送流程 = append → save（活动路径线性链，parentId 按线性序推导，运行态节点剔除且链指针改写为其 `{runId}:marker`、activeLeafId 同步改写）→ start_chat（Rust 侧 user 不在史时兜底补落）。启动/会话进入时 `load_session_tree → import()` 收养 canonical 树（turn 级形态）；`E_SESSION_REV` 时 load 校正 revision 重试一次。运行中树上保留运行态节点渲染（不重载），重启后树即 canonical 形态。
- 树操作 API 钉死（0.15.31 实测，S4）：编辑=`MessageRuntime.composer.beginEdit()`+`send()`（语义=在原消息父下 append 兄弟分支）、分支切换=`switchToBranch({branchId})`、导出=`thread.export()`。注意点：import 时 LocalRuntime 将非 complete 的 assistant status 改写为 incomplete/cancelled（M1 只落 complete，不受影响）；`fromThreadMessageLike` 丢弃空白 text part、`isError` undefined→false 归一（语义等价，比对口径已归一）。canonical 追加（start_chat 的 user、run 产物）与前端树同步双写：canonical 追加总是先发生且 revision++；前端以最新 revision 为 base 同步，永不覆盖只追加。精确结构以转换层 `ui/src/chat/tree-persistence.ts` 为单一事实源。
- **【M2】compaction 条目的树承载（04 号票定稿，取代票面"参照 runMarker"建议形态）**：compaction 条目**不投影为树节点**——§6.1 该条目无 `parentId` 字段，且 run 开始前压缩时本次 user 条目已先行落盘（parent 指向压缩范围链尾），链上插入任何节点都会与真实后续条目构成兄弟分支，破坏 assistant-ui 分支切换语义。定案：① `load_session_tree` 返回结构增 `compactions: StoredCompactionEntry[]`（与 messages 并列的投影面，message 面仍不含 compaction）；② 前端树全量保留被压缩历史（原始历史永不丢、display 全量），时间线在消息列表顶部按压缩条目渲染"已压缩早期上下文"分隔提示（非消息体）；③ `entriesToExported`/`toWire` 不产 compaction 节点（save 载荷与史册天然无冲突，无 E_SESSION_REV 面）；④ wire 重建的压缩边界以后端史册为准（start_chat 命令内读最近 compaction，按 `cutEntryId` 过滤前端传入序列并注入 summary，§6.2），不依赖前端携带。

### 6.4 修订号与并发

revision 单调递增，存于 session meta 行与 index.json。`save_session_tree` 校验 baseRevision == 当前值；不等返回 E_SESSION_REV，前端重载后重试（分支冲突极少见：单用户单实例）。

### 7.2 分段与封口

- 段封口条件（仅在安全点检查：run 终态后、ask 关闭后）：条目数 ≥200 或字节数 ≥512KB。
- 封口时写 `.segmeta.json`（段清单 + 每段 head 条目哈希）；恢复时校验 headFingerprint：不匹配只新增新段、绝不截断既有段。
- 每段文件内条目按追加序线性排列；段内禁止拆分同一 run 的 message 组（安全点机制保证）。
- `save_session_tree` 载荷为 assistant-ui `export()` **全树**（含全部分支节点）；其导出顺序与 Rust"父先子后仅追加缺失节点"天然匹配（S4 实证），封口与 headFingerprint 纪律不变。

### 7.3 持久化时机与 fsync 策略（NFR-06 解释）

| 事件 | 持久化动作 | fsync |
|---|---|---|
| start_chat user 消息 | 追加 message 条目 | 是 |
| 每个工具结果 | 追加 toolResult part 所属 assistant 条目（逐 turn 落）+ toolres 边车 | 是 |
| turn 文本完成 | 追加该 turn assistant 条目（文本在 turn 内仅内存，turn 结束一次落盘） | 是 |
| run 终态 | 追加 runMarker + meta(revision) + index 更新 | 是 |
| 压缩完成（【M2】04 号票增行） | 追加 compaction 条目（走既有 append 通道，计入 §7.2 封口计数；触发点与安全点重合，无段内拆分组问题）+ meta(revision) | 是 |
| steer 消费（【M2】06 号票增行） | 追加 steer user 条目（id=`{runId}:steer:{n}`，消费点直接 append_canonical，§5.5） | 是 |
| 文本流中途崩溃 | 该 turn 未提交 → 重启后该 run 标记 interrupted（无半行） | — |

**NFR-06 的实现口径**：已提交（上表落盘点）历史零丢失；进行中 run 的未完成 turn 不入史、重启标记 interrupted——这是有意设计而非缺陷。

**实现锚点（15 号票）**：① user 条目 = 前端发送前 save（§6.3 双写协议）落盘，start_chat 侧同 id 幂等兜底；② turn 条目/工具条目/runMarker 由 host 层 `RunRecorder`（`FrameSink` 装饰器，零侵入 RunLoop）从帧流聚合落盘——usage 帧收口文本条、批内最后 toolResult 收口工具条（配对相邻、args 规范化 compact 保序）、runEnded 收口 marker 并 upsert index.json；③ toolres 边车在工具执行器完成点逐结果原子写（§7.5）；④ 崩溃恢复在 `load_session_tree` 读时修复：canonical 形态条目（id 前缀 `{runId}:`）出现而无对应 marker → 追加 interrupted 修复行（endedAt 省略）；⑤ 落盘失败记日志不中断 run（帧面可用性优先，M1 取舍）。

### 7.4 原子写与锁（util/atomic.rs、storage）

- 所有整文件（config/index/prefs/ui-state/segmeta）写法：临时文件同目录 + `fsync` + rename（Windows `MoveFileExW MOVEFILE_REPLACE_EXISTING`）。
- 进程内锁：`MutexMap<SessionId>` 串行化同会话存储操作；全局 `index_lock` 在会话锁内获取（锁序：session → index，禁止逆序）。
- M1 单进程 + 单实例插件 → 无跨进程写并发；跨进程写锁（CW FileCoordinator）留 1.x。

### 7.5 toolres 边车与恢复

`ToolOutcomeJson` 全量写 `<callId>.json`；`load_tool_outcomes` 批量返回。卡片恢复：前端渲染历史 toolCall part 时按 callId 拉取。GC：会话删除时随目录删除；单文件超过 5MB 拒绝入边车（引用 spill 文件路径代替）。

### 7.6 配置协调器（FR-14-03）

写 config 流程：入参校验/归一化 →（涉 newKey 时先走 §9.4 钥匙串协议）→ 临时文件写入 → fsync → rename → 内存缓存热替换 → 返回归一化结果。意向日志（intent.json）在钥匙串步骤前落盘，成功后删除；崩溃后重启发现意向日志则提示用户重试（不自动重放写操作）。

### 8.4 edit 算法（伪代码，FR-04 表 edit 行）

```
输入：path, oldText, newText, version?(sha256(原文件字节)前16hex)
1. safe_join(path) → 越界 E_PATH_OUTSIDE_ROOTS
2. 读原文件 bytes；version 给定且不匹配 → E_EDIT_VERSION_STALE（若仍可唯一匹配则降级为警告执行，结果标注）
3. 匹配 oldText（三级，每级仅接受唯一命中，绝不猜）：
   L1 精确字节匹配
   L2 整块缩进平移：oldText 整体去掉公共缩进后在全文按行试每种缩进回填
   L3 逐行首尾空白归一匹配（记录映射）
   0 命中 → E_EDIT_NO_MATCH；≥2 命中 → E_EDIT_AMBIGUOUS（模型须补充上下文）
4. 组内预演（Q32，07 号票落地）：同文件多个 edit 统一基于修改前内容算区间（L1/L2 字节区间、
   L3 行区间统一归算为归一化 LF 域的字节区间），非重叠允许合并原子提交；区间重叠，或同文件
   混入 write（write 语义为"仅新建"，与 edit 互斥），或同路径多个 write → 拒绝后续冲突调用
   （E_INVALID_ARG + 冲突说明回喂；源序首个写调用保留执行资格）。组内任一 edit 匹配失败
   （NO_MATCH/AMBIGUOUS）→ 整组不合并，按源序逐个独立执行（各出各的匹配错误结果）。
5. 提交（07 号票批次事务）：备份原文件到同目录 tmp → 接受成员按 start 降序在归一化文本上
   应用全部替换 → EOL 还原 → 单次原子落盘（tmp + fsync + rename，即 fsync 步）→ 任一失败
   从备份恢复原文件（回滚整组，写入未生效）→ 成功后清理备份。合并提交使组内全部 edit 一次
   rename 生效或全部不生效，各成员结果带同一最终 version 与各自 lineChanges。
6. EOL 保持：检测原文件 CRLF/LF，写回时还原
```

### 8.6 计划门（FR-06-02 默认"有计划即守门"）

- PlanState{items, approvedSnapshot?, approvedAt?}。用户在计划卡点"批准" → 冻结快照。

### 8.7 fence v0.1 规则（FR-05-05 P0 部分）

1. 黑名单（正则集，命中即 E_FENCE_BLOCKED）：`rm -rf`、`sudo/su`、`shutdown/reboot`、`mkfs`、`dd of=/dev/`、`curl|wget … | sh/bash`、`git push --force`、`chmod -R 777 /`、`> /dev/sd`、Windows `format/rd /s /q`。
2. plan 档只读白名单：`ls/cat/head/tail/wc/find/rg/grep/git status|diff|log|show/node --version/python --version` 等子命令集。
3. 写信号启发（非 plan 档）：重定向 `>`/`>>`、`tee`、`sed -i`、`npm i/pip install/make/cargo build` 等 → confirm_each 审批；无信号 → 按档位。
4. AST 写目标分析（tree-sitter bash/powershell）为 P1（FR-05-05 P1 部分）；v0.1 明确**不 fail-open**：黑名单或写信号判定异常时按 Confirm 处理。

**【M2】fence AST 管线**（替换规则 3 的写信号启发）：

```
解析（tree-sitter bash / powershell grammar）
  ├─ 解析失败 → fail-closed：按 Confirm 处理（改进 CW 的词法回退漏洞）
  ├─ 写目标提取：重定向 > >>、tee、sed -i、rm/mv/chmod/chown、install/cp、mkfs、dd of=
  │    及"管道左侧含写命令"的保守合并
  ├─ 字面量掩码：引号外变量出现在写路径 → 保守按 Confirm（防 $HOME/.. 逃逸）
  └─ 写目标四象限判定：
       词法在 roots 且 canonical 在 roots   → Allow（auto_edit+ 档直写）
       词法在 roots 但 canonical 逃逸       → Confirm（symlink 逃逸）
       词法不在 roots                      → Confirm / Block（删除类直接 Block）
       无法 canonicalize（目标不存在且父链异常）→ Confirm
  git 子命令分类表：status/diff/log/show 只读；push/commit/merge/rebase 写（默认 Block push --force、其余 Confirm）
```

**【M2】写入后检查（FR-04-06）**：设置 `{ enabled, command, timeoutSec: 30, tailChars: 3000 }`；create/edit 成功后在项目根执行（`{file}` 占位替换为相对路径），退出码与尾部输出写入工具结果 `data.check` 回喂模型，驱动自修复。

**保护边界与命令审计（Q23，经 Q24–Q26 更新）**：AST/路径规则保护可识别写目标，不构成任意脚本/MCP 的系统隔离。已知禁区写入硬拒；可靠只读操作按既有权限执行；灰区 command 由无工具单次模型审计返回 Allow/Block/Ask 及理由。低风险可自动放行，但权限档、禁区、计划范围、公共操作仅主代理及明确人批要求不可豁免；证据不足或审计超时/离线/坏输出转人工并显示原因，取消同时取消审计。MCP 保持既有审批；full_access/白名单/自动确认不替代明确人批。既有 workspace/ 工作区写权限保留。见 36 号票与 ADR-0002。

**异步接线**：ToolGate::judge 保持同步，复用 host 全批挂起后的异步流程和 complete_once，不持锁请求模型。审计结论绑定本次调用与实际输入，区别于人工批准；恢复仍重查硬规则，不使用在硬围栏前直接 Allow 的签名缓存承载模型结论。**Q27–Q29 已定**：设置页可指定审计模型，未指定跟随当前会话；独立提示词不带全历史。应用在授权目录只读收集相关脚本/命令定义/用户目标/批准范围，审计器无工具，证据不足转人工。单次总等待上限 15 秒，期间显示审计中，工具卡给出结论与简短理由；实际返回的用量计入会话累计，不增主任务轮次。具体接线及字段回写见 36 号票。

### 8.8 命令输出治理

超时默认 120s（1–600）；stdout+stderr 合流清洗 ANSI/OSC；>96KB 全量 spill 至 `logs/spill/<callId>.txt`（24h 清理），工具结果只带尾部 16KB + spill 路径；进程组（Unix）/Job Object（Windows）在超时/取消时整树收割。

### 8.9 文档工具管线【M3】（FR-12-05/06/07）

- 前端：PDF.js 阅读器与 xlsx 结构化预览卡（读 `read_workspace_file` 返回的结构化数据）。

### 8.10 浏览器工具【M3】（D18）

## 9. 安全设计

### 9.1 路径边界 safe_join（FR-05-06）

```
safe_join(roots, path):
  拒绝：空、包含 "\0" 或控制字符、Windows 保留名（CON/PRN/AUX/NUL/COM1…）
  解析为绝对路径（相对路径相对项目主目录）
  规范化后 canonicalize（解析符号链接）
  要求 canonical 前缀 ∈ roots 的 canonical 集合（roots = 项目主目录 + `<data_root>/workspace/` 子目录 + M1: 无 extra_roots；C-8 复判 2026-10-28 收窄——数据目录本体退出 agent 可见面，config/sessions 等存储内部文件天然免疫）
  命中即通过；否则 E_PATH_OUTSIDE_ROOTS
  full_access 不解除本检查
```

删除守卫（delete 工具 P1，write 覆盖语义复用）：目标 canonical 为 文件系统根/家目录本身/.git/系统目录（/System32、/usr 等）→ E_DELETE_GUARDED。

### 9.2 SSRF 管道（P1 实装，规格先行）

### 9.7 MCP 信任与连接治理【M2】（FR-08 域）

- **TOFU 启动信任（FR-08-03）**：连接（stdio 启动/HTTP 握手）前计算指纹 `(scope, projectId?, name, canonicalConfigPath, sha256(config))`；无信任记录 → `ask:opened` 携 `AskPayload{kind:"mcpTrust"}`（本次 / 记住此版本 / 拒绝）；"记住"落 `~/.craftwave/trust/mcp.json`（`[{ fingerprint, decidedAt, decision: "remember"|"revoke" }]`，§7.7 同款形状；v2.5 已废除钥匙串，08 号票回写：原"写 keyring 账户 craftwave.trust.v1"按 trust 域文件存储）；配置指纹变更 → 重新询问。
- **调用审批（FR-08-04）**：server 未声明 `read_only` 且未开 `always_allow` → 即便 full_access 也确认；"始终允许"热更新策略不重启连接；plan 档全部 MCP 工具过滤（§8.5 注）。
- **动态工具许可（Q44）**：清单自动同步，但新增工具或输入 schema 变化不继承旧免审批许可，首次调用重新确认，旧服务器级 read_only/always_allow 不自动覆盖新版本。许可绑定服务器身份、原始工具名及已确认输入 schema；仅描述变化可提示更新，不扩大许可。read_only/always_allow 以用户确认配置为准，远端 annotations 不得自行升级权限；工具版本许可与服务器启动信任分别核验。**许可存储字段（08 号票定案落地）**：`trust/mcp-tools.json` 条目 `{ serverFingerprint, toolName, schemaHash, decidedAt }`——三元组（服务器启动指纹 + 原始工具名 + 已确认输入 schema 的 SHA-256 前 16 hex）全等才免审批；审批「始终允许（当前版本）」授予、启动信任 revoke 连带撤销该指纹下全部许可。
- **连接池（FR-08-05）**：key=`(scope, projectId, name, canonicalPath)`，LRU ≤16；状态机 Starting→Ready→Stopped/Error，每次迁移发 `mcp:status` 事件（§3.5 M2 键）；generation 计数防旧握手复活；断线指数退避重连（1s/2s/4s…封顶 60s）；单次工具调用超时取配置 `timeout` 秒数（缺省 60，合法区间 1–600，08 号票定案）；stdio 子进程进程组/Job Object 回收。
- **结果未知与重连（2026-10-29 用户确认 Q14）**：连接可自动恢复；已发出而结果未知的工具调用不得自动重放，即使 server 声明 read_only。向主代理报告“可能已执行”，由主代理先核查实际结果再决定是否重试；未知结果不得被当作“未执行”的普通失败而触发通用自动重试。**错误/结果形态（08 号票定案落地，§3.6 已补录）**：请求未发出或明确未完成 → `E_MCP_DISCONNECTED`（普通失败，可直接重试）；请求已发出但断连/超时 → `E_MCP_RESULT_UNKNOWN`（ok=false，data 带 `resultUnknown: true` 结构化标记，错误消息带「先核查实际结果再决定重试」的行动指引进模型通道）。
- **工具接入**：MCP 工具经 rig-rmcp 转 `DynamicTool` 注册（工具名归一：合法字符化 + 碰撞 `__2` 后缀 + 反向映射还原）；`tools/list_changed` 自动同步；资源读取 `mcp_read_resource`（M3）与 `resource_context` 动态注入（M3）。

### 9.8 项目资源信任【M2】（FR-05-10）

- 信任对象：`<home>/.craftwave/` 全部资源（skills / memory / mcp.json / project 指令 AGENTS.md、CRAFTWAVE.md、CLAUDE.md）。
- 首次加载：指纹=资源内容 SHA-256 → `AskPayload{kind:"projectTrust"}`（本次会话允许 / 记住此版本 / 拒绝）；决策写 `trust/project.json`（§7.7）；未信任资源不注入系统提示且工具访问拒绝（E_PROJECT_UNTRUSTED）；内容变更 → 重新询问。
- 全局作用域（`~/.craftwave/skills/`、`memories/`）首用同样走信任（scope=global）。

- **worktree 信任与版本（2026-10-29 用户确认 Q19/Q20）**：应用管理的 worktree 归属原项目，同资源同内容沿用对应作用域内的信任，内容改变重问，其他项目不继承。MCP 指纹只归一副本来源路径，实际启动配置变更仍重核。每个 run 固定项目指令与技能版本，description 和正文同版本；变更下一 run 加载并核验，旧版不可得不替换新版继续。安全权限撤销立即生效。指纹/版本字段与接线见 08/09/24 号票。

- **技能整体版本（Q21 用户确认）**：信任覆盖技能说明与随附脚本、模板等资源，附属内容变化亦在下一 run 重核；不能沿用旧 SKILL.md 指纹读取新版附属资源。详见 09/24 号票。

- **技能信任与版本的字段级细则（09 号票回写，实现以此为准）**：
  - **目录清单**：三来源根 = 内置（随应用资源分发：打包态 `<Resource>/resources/skills/`，开发态回退源码树 `src-tauri/resources/skills/`）、全局 `<data>/skills/`、项目 `<项目主目录>/.craftwave/skills/`（临时会话无项目来源）；每技能 = 一级子目录 + 目录内 `SKILL.md`（YAML frontmatter `name`（必填，≤64 字符 `[a-zA-Z0-9_-]`）+ `description`（必填）），frontmatter 额外字段忽略（兼容 Claude 技能目录格式），目录内附加资源文件按相对路径随正文可用；frontmatter 解析失败的目录跳过不入索引；同名（frontmatter `name`）覆盖优先级 内置 < 全局 < 项目（后扫者胜，来源标记进 `skill_list`）。
  - **路径边界**：扫描不追随符号链接（目录与文件均为 symlink 的条目跳过）；防御上限 = 每技能目录参与指纹的文件 ≤512 个且总量 ≤64 MiB，超限该技能不入索引（防 symlink 环与异常目录拖垮 run 启动）；技能正文与附加资源只读，模型不经技能机制写技能目录。
  - **版本摘要算法（Q21 整体信任指纹）**：`sha256("craftwave-skill-v1|" + name + "|" + Σ(相对路径 + "=" + sha256(文件字节)) )`，Σ 按相对路径字典序拼接、`|` 分隔——SKILL.md 与全部附属资源任一变化（新增/删除/改动）都改变指纹，下一 run 重新核验信任；run 开始时快照 SKILL.md 正文全文进内存（run 内 `skill` 工具只读快照，不触盘），旧版本天然可得，"旧版本不可得"分支不触发（若未来改按需读盘须重引入该分支）。
  - **信任接缝（24 号票完整机制落地前的最小版）**：`AskPayload{kind:"projectTrust"}` 载荷 = `{ name, scope: "global"|"project", fingerprint(前 16 hex), options: [allow_once/remember/deny] }`；应答走 `AskAnswer::Approval`（optionId），协议面不新增应答形态。内置技能豁免信任（与应用同源分发）；`remember` 写 `trust/project.json` 条目（`resourceName`=技能名，decision 值域 `remember`，revoke/撤销 UI 随 24 号票）；`allow_once` 记进程内存会话信任集（同会话下一 run 免问，重启失效）；`deny` 不产生记录（TOFU 同 MCP 口径），下一 run 重新询问。询问在 run 开始装配时同步等待（用户主动发消息触发，仿 MCP 连接询问挂应用级询问桶）；拒绝 → 该技能本 run 不注入清单且 `skill` 调用回 `E_PROJECT_UNTRUSTED`。

### 10.2 ChatModelAdapter（核心，官方 Tauri 路径）

```ts
// chat/runtime.ts —— 伪代码级完整设计
const tauriChatModel: ChatModelAdapter = {
  async *run({ messages, runConfig, abortSignal }) {
    const { sessionId } = useSessionStore.getState();
    const channel = new Channel<SequencedFrame>();
    const buf = new FrameBuffer();              // 累积器：parts 数组 + runMetrics 转发
    channel.onmessage = (f) => { buf.push(f); runMetrics.ingest(f); };
    const { runId } = await invoke("start_chat", {
      sessionId, messages: toWire(messages), runConfig, channel,
    });
    const abort = () => invoke("cancel_run", { sessionId });   // 不 await
    abortSignal?.addEventListener("abort", abort, { once: true });
    try {
      for await (const snapshot of buf.snapshots()) {          // 64ms 节流快照迭代器
        yield buf.toResult(snapshot);                          // ChatModelRunResult：累计 parts
      }
    } finally {
      abortSignal?.removeEventListener("abort", abort);
      metrics.final(buf.usage);                                 // 计数条定格
    }
  },
};
// toResult：text/reasoning → 对应 part；toolStarted/Args/Result → 镜像工具的
// tool-call part（argsJson 累积，半截 JSON 由 toolkit 卡片以"参数准备中"渲染）；
// runStarted/runEnded → data-runMarker part（折叠分组锚点，见 10.4）
```

助手消息 part 顺序即帧到达顺序；每次 yield 为**全量累计快照**（assistant-ui 语义：替换而非增量）。

### 10.3 镜像工具与卡片（D11）

- `defineToolkit`（0.15.31 实存，从 @assistant-ui/core/react re-export）声明 9 个 P0 工具的**渲染副本**：`type:"frontend"`、**不带 execute**（不执行业务）；name/参数 schema 与 Rust ToolSpec **同一份来源**（Rust 测试导出 `ipc-manifest.json`，前端测试校验一致性，§12.3）。卡片组件直接作为条目 `render` 字段——`makeAssistantToolUI`/`useAssistantToolUI` 已 @deprecated，不采用。
- 挂载方式（S1 实测钉死）：`Tools` 是 @assistant-ui/tap resource 工厂，**不能当 JSX 元素**；经 `AssistantRuntimeProvider config={AuiConfig({ tools: Tools({ toolkit }) })}` 注入（config 为纯数据可提模块级）。`MessagePrimitive.Parts` 的 children 对 tool-call part 返回 null 时自动 fallback 到注册卡片。
- 结果注入（S1 修正）：**ChatModelAdapter 把 FrameBuffer 累积的 toolResult 帧直接写进 tool-call part 的 `result`/`isError` 字段**，part 级 running→complete/error 状态机原生生效。设计原「`execute()` 注册 pending Promise、toolResult 帧到达后 resolve」**作废**——0.15.31 local runtime 不触发 frontend tool 的 execute（ToolInvocationTracker 仅接 external-store runtime，§10.2 的 ChatModelAdapter 路线与之互斥）；D11 决策（复用原生状态机）不变、依据更扎实。
- 参数流式：半截 JSON 参数增量以 `argsText` 原文展示（「参数准备中」态）；args 用 assistant-stream 的 `parsePartialJsonObject` 产出（含 partial-parse 元数据；ui 需**显式声明依赖 assistant-stream**，pnpm 隔离布局下传递依赖不可直接 import），卡片内 `useToolArgsStatus().argsStatus` 区分 streaming/complete。不闪烁不重建已测试钉死（每个 toolCallId mount 恰好 1 次，全程零 unmount）。
- 卡片（每工具一个 React 组件，规格级）：
  - `read`：路径 + 行区间 + 预览展开（首 50 行，读全文调 read_workspace_file）。
  - `write/edit`：unified diff 视图（+N/−N 徽标；edit 用 hunks 结构直接渲染）。
  - `command`：命令行 monospace + 输出折叠（默认尾部 20 行）+ 退出码徽标 + spill 链接。
  - `grep/list_files`：命中计数 + 结果列表（上限展示 100）。
  - `plan`：计划卡（FR-06-01 双呈现：消息内 + 右栏面板，批准按钮冻结快照）。
  - `ask/suggest`：不渲染为卡片（AskPanel/ghost hint 承载）；M1 落地注记（14 号票）：ask 落地为极简状态卡（标题 + 等待提示，防无注册卡时空白 fallback），问题本体与作答仍在 AskPanel。

### 10.4 折叠分组与总结（FR-01-10）

- runMarker part（runStarted/runEnded 成对）划分消息区；Thread 渲染组件按"当前 runMarker 区间"分组。
- 组内渲染：过程 parts（reasoning/工具卡/计划更新）默认展开（运行中）→ 收到 runEnded data part 后 3s 内收起为摘要行 `⚙ {toolCount} 次工具调用 · {duration}`；区间内**最后一个 stepStarted 的 text parts** 即最终答复（多个 text part 按序拼接为一段），保留在折叠区外常显；更早 turn 的零星 text 归入折叠区。
- 历史加载：runEnded 存在的区间默认收起；点击摘要行展开（过程数据来自持久化 parts + toolres 边车补全）。
- 建议提示词（FR-06-09）：`askHint` store 订阅 run:suggestions → Composer 内 ghost span（输入为空时整句 / 前缀匹配时补尾部）；Tab 优先级：触发符菜单 > hint；接受=填入不发送。

### 10.5 Token 计数条（FR-01-13）

`runMetrics` store 持有 {rate, turnUsage, sessionUsage}：rate=usage 帧 rate 或 TextDelta 窗口自算（TTFT 记首帧时间）；turnUsage 按 runId 清零累计；sessionUsage 以 tokens:update 为准（M1 标量回填，M2 按下文 Q37 恢复四口径）。三个数字常驻 Composer 下方；hover Popover 拉四口径明细（缓存命中率=cacheRead/(input+cacheRead)）、上下文进度条（本次实际上下文占用估算/当前模型 contextWindow，0.6 阈值标线；与会话累计消耗区分）。后台零工具小调用（suggest、标题生成，C-9 已定）计入 sessionUsage，不计入 turnUsage（runEnded 后轮次数字冻结）；用量 Popover 不为后台调用单列明细行；小调用失败静默放弃（不重试、无提示），但 Q39 要求已返回 usage 仍记账，未知用量不伪造，不能承诺失败免费。

**用量恢复补充（Q37）**：M2 由 20 号票补齐 run/会话四口径权威持久记录与重启恢复，取代仅从 SessionMeta.totalTokens 回填的 M1 标量方案；调用时模型名快照不随当前配置删除或改名丢失。沿用现有用量展示入口，不新增复杂 run 明细列表；日/模型统计保留 90 天，不能用缺少会话维度的日聚合恢复会话明细。

**用量归属（Q39/Q40）**：每次响应 usage 按当时本地日期固定记账，跨日 run 可拆日、之后切时区不重排历史。会话累计包含主代理、子代理及辅助调用，Composer 本轮只含主代理自身，子代理面板显示各自消耗；按实际模型归属，不重复汇总。runs 仅主 run（含队列自动发起），子代理和辅助调用不增加该次数。

**运行中切模型/thinking**：FR-02-07 的“下一请求生效”覆盖同一 run 内的下一次模型请求。当前请求不被打断，请求间重新读取会话偏好并更新所需客户端/参数，再做预算与图片能力检查；只在 start_chat 读一次快照不满足要求。实施与回归由 18 号票承载。

## 11. Provider 适配层

### 11.1 模型解析（FR-02-07）

优先级：会话当前模型偏好（初始来自 RunConfig.modelId）> AppConfig.activeModelId。`ResolvedModel { provider: ProviderConfig, model: ProviderModel }` → RigAgentBackend 内按 apiFormat 构造 rig Model：openai_chat→OpenAI 方言（baseUrl 可覆写）；anthropic_messages→Anthropic；openai_responses→Responses API。客户端在 run 内复用，但每次模型请求前须读取最新会话模型/thinking 偏好，切换时更新所需客户端和参数，不打断正在进行的请求。三协议完整接入由 M2 38 号票补齐现状欠账，并接通 18/19 号票；不把当前仅支持 openai_chat 的限制视为最终范围。Key 池已砍出 M2，见里程碑规格。

### 11.2 Key 池【M2 实装，M1 接口定死】（FR-02-12）

```rust
struct KeyHealth { index: usize, state: KeyState, last_error: Option<String>, until: Option<Instant> }
enum KeyState { Active, Cooldown, Failed }
```

状态机（同供应商全 Key 共享健康视图，仅内存态——重启清零可接受：冷却本质是短时熔断保护）：

| 事件 | 迁移 |
|---|---|
| 请求 auth 类失败（401/403） | 该 Key → Cooldown(30min)；立即换下一 Active Key 重建客户端重试同请求（换 Key 重试 ≤ 池大小次） |
| 其他可重试失败 | 该 Key → Cooldown(10s × 2^n，封顶 30min)；同上换 Key |
| 请求成功 | 该 Key → Active（其余 Key 冷却不变） |
| 全部 Cooldown | 不等待：终态报错并在 uiSummary 列出最早解冻时间；autoConfirm/自动重试不适用 |

M1：单 Key 直用（数组结构就位）。Key 数量上限 10/供应商；增删经 save_provider（keyring 数组整体覆写，generation+1）。

### 11.3 错误分类映射（FR-03-04）

| rig/provider 现象 | 分类 | 动作 |
|---|---|---|
| 401/403/invalid key | auth | 不重试；Key 池轮换（M2）；帧内联提示 |
| 402/quota | billing | 不重试，提示充值/换 Key |
| 429 | rate_limited | 退避重试 ≤6 次（1s/2s/4s/8s/8s/10s） |
| 400 | bad_request | 一次 sanitize 重试（剥离空 text/异常 tool_call 组合；thinking 回传按粘性标记补 reasoning_content）；再败即终态 |
| 5xx | server | 退避重试 |
| 流解析异常 | protocol | 退避重试；连续 2 次终态 |
| 连接/超时/DNS | network | 退避重试 |

### 11.5 订阅/余额适配器【M2】（FR-02-15）

`trait QuotaAdapter { fn matches(&self, baseUrl) -> bool; async fn fetch(&self, keys) -> Result<QuotaData> }`；按 Base URL 主机路由，首批 7 家：DeepSeek、Kimi、MiniMax（国际/中国双域名）、智谱、Z.ai、OpenCode。六态 `ok / error / invalid / rejected / no_key / unsupported`；刷新策略：Inspector 配额页可见时每 5min + 手动 + 切换 provider 即时；快照原子写 quota.json，离线显示最近快照与 fetchedAt；失败静默降级（占位"暂不能查询"），永不阻塞聊天。

### 11.6 订阅 OAuth【P3 占位】（FR-02-16）

触发条件：1.x 用户需求信号明确后再立项。技术路线（PRD 定稿）：优先 rig 原生 `chatgpt`（Codex 订阅）与 `copilot` provider，零额外协议开发；登录 UI 复用 AskPanel（AskPayload 增 `kind:"oauth"`）+ 系统浏览器回调 loopback 端口；token 刷新由 rig provider 内部处理；Claude 逆向方案仅技术储备（合规灰区，不默认实现）。
